## 1 总体原则

### 1.1 核心理念

| 原则 | 说明 |
| --- | --- |
| **安全第一** | 涉密数据、权限控制、出网闸门是红线，不可妥协 |
| **可维护性** | 代码清晰胜过聪明，显式胜过隐式 |
| **可测试性** | 所有业务逻辑必须可单元测试 |
| **可扩展性** | 使用配置和注册机制，避免硬编码 |
| **一致性** | 团队内保持统一风格，降低理解成本 |

### 1.2 强制性要求（不可违背）

✅ **必须遵守的红线：**

1. **敏感数据禁止云端发送，涉密内容拒绝AI处理** - 所有模型调用必须经过出网闸门；内部内容要求获准的精确主机白名单
2. **租户隔离不可绕过** - 检索层和数据访问层必须强制注入租户条件
3. **审计日志不可篡改** - 审计表只追加，不更新不删除
4. **阶段流转不可自动化** - 党员发展阶段变更只能通过人工接口
5. **引用必须可核验** - 生成内容的引用必须回查真实性
6. **配置优于代码** - 易变项（时限、权重、模型清单等）必须外置配置

以实际目录为准。当前没有 `app/modules/`、`app/events/`、`app/integrations/`、通用提示词版本登记或独立组织生活路由；未来规划不能作为已实现能力。

### 2.2 模块组织原则

| 原则 | 说明 | 示例 |
| --- | --- | --- |
| **按功能分模块** | 沿现有分层按业务命名，不额外复制模块骨架 | `api/v1/study.py`、`services/study_service.py`、`schemas/study.py` |
| **业务自治** | 同一业务的service、schema和model各自在对应层维护 | `services/study_service.py`、`schemas/study.py`、`models/study.py` |
| **禁止循环依赖** | 模块间通过接口或事件通信 | 不允许 A 引用 B，B 又引用 A |
| **分层清晰** | API → Service → Chain → Model | 上层可调用下层，下层不可调用上层 |

## 4 命名规范

### 4.1 Python 命名

| 类型 | 规范 | 示例 | 禁止 |
| --- | --- | --- | --- |
| **模块名** | 小写+下划线 | `qa_service.py` | `QAService.py` |
| **类名** | 大驼峰 | `QAService` | `qaService` |
| **函数名** | 小写+下划线 | `get_user_info()` | `getUserInfo()` |
| **变量名** | 小写+下划线 | `user_name` | `userName` |
| **常量名** | 全大写+下划线 | `MAX_RETRY_COUNT` | `maxRetryCount` |
| **私有成员** | 单下划线前缀 | `_internal_state` | `__private` |
| **类型变量** | 大驼峰 | `T = TypeVar('T')` | `t` |

### 4.2 数据库命名

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| **表名** | 小写+下划线，复数 | `users`, `knowledge_docs` |
| **字段名** | 小写+下划线 | `created_at`, `tenant_id` |
| **索引名** | `idx_表名_字段名` | `idx_users_email` |
| **外键名** | `fk_表名_字段名` | `fk_members_branch_id` |
| **唯一约束** | `uk_表名_字段名` | `uk_users_email` |

### 4.3 API 命名

| 类型 | 规范 | 示例 |

## 5 注释与文档规范

### 5.1 注释原则

| 原则 | 说明 |
| --- | --- |
| **代码即文档** | 优先写清晰的代码，而非依赖注释 |
| **注释解释"为什么"** | 不要注释"做什么"（代码已经说明了） |
| **保持同步** | 修改代码时必须同步更新注释 |
| **TODO 必须有责任人** | `# TODO(zhangsan): 补充异常处理` |

### 5.2 函数文档字符串（必须）

**所有公开函数必须有 docstring，使用 Google 风格：**

```python
def hybrid_retrieve(
    query: str,
    tenant_id: str,
    top_k: int = 5
) -> list[RetrievalChunk]:
    """混合检索：向量检索 + 关键词检索 + 重排。

    本函数实现知识库的混合召回策略，先分别执行向量检索和关键词检索，
    再融合排序并使用交叉编码器重排，最后强制过滤租户、可见范围和时效。

    Args:
        query: 用户问题
        tenant_id: 租户ID（自动注入，不可绕过）
        top_k: 返回片段数，默认5

    Returns:
        检索到的片段列表，按相关性降序排列，每个片段包含：
        - content: 片段内容
        - metadata: 元数据（文件名、文号、来源等）
        - score: 重排后的相关性分数

    Raises:
        ValueError: 当 top_k < 1 时
        TenantIsolationError: 当租户ID为空时（框架级错误）

    Note:
        - 本函数在检索层强制注入租户过滤条件，业务代码无法绕过
        - 默认排除已废止文件，历史查询需显式传入 include_expired=True

    Example:
        >>> chunks = hybrid_retrieve("入党流程", tenant_id="school_001")
        >>> for chunk in chunks:
        ...     print(chunk.content, chunk.score)
    """
    pass
```

### 7.2 请求响应格式

**统一响应结构：** 业务接口使用 `app/schemas/common.py` 的 `APIResponse`。健康检查、文件/TXT/ZIP导出采用专用响应；错误详情由 `app/main.py` 统一处理，不能回显密码或请求原始正文。

```python
from pydantic import BaseModel
from typing import Generic, TypeVar, Optional

T = TypeVar('T')

class APIResponse(BaseModel, Generic[T]):
    """统一API响应格式"""
    code: int                    # 业务状态码
    message: str                 # 提示信息
    data: Optional[T] = None     # 响应数据
    trace_id: str                # 请求追踪ID

# 成功响应
{
    "code": 0,
    "message": "success",
    "data": {...},
    "trace_id": "req_123456"
}

# 失败响应
{
    "code": 40302,
    "message": "租户隔离校验失败",
    "data": null,
    "trace_id": "req_123456"
}
```

**分页响应：** 下方为约定示例；当前接口常以 `data.items/total/page/page_size` 返回，不能假设存在通用 `PageResponse` 类或每个接口都有 `has_next`。

```python
class PageResponse(BaseModel, Generic[T]):
    """分页响应"""
    items: list[T]
    total: int
    page: int
    page_size: int
    has_next: bool

# 响应示例
{
    "code": 0,
    "message": "success",
    "data": {
        "items": [...],
        "total": 100,
        "page": 1,
        "page_size": 20,
        "has_next": true
    },
    "trace_id": "req_123456"
}
```

### 7.3 状态码规范

| HTTP 状态码 | 业务码 | 说明 | 使用场景 |
| --- | --- | --- | --- |
| 200 | 0 | 成功 | 正常响应 |
| 400 | 40001 | 参数错误 | 请求参数不合法 |
| 401 | 40101 | 未认证 | Token 缺失或过期 |
| 403 | 40301 | 权限不足 | 无权访问资源 |
| 403 | 40302 | 租户隔离校验失败 | 跨租户访问 |

## 9 安全开发规范

### 9.1 敏感数据处理

**脱敏规则：**

```python
def mask_id_card(id_card: str) -> str:
    """身份证号脱敏：保留前6位和后4位"""
    if len(id_card) < 10:
        return "***"
    return f"{id_card[:6]}****{id_card[-4:]}"

def mask_phone(phone: str) -> str:
    """手机号脱敏：保留前3位和后4位"""
    if len(phone) < 7:
        return "***"
    return f"{phone[:3]}****{phone[-4:]}"

def mask_email(email: str) -> str:
    """邮箱脱敏：保留首字母和@后内容"""
    parts = email.split('@')
    if len(parts) != 2:
        return "***"
    return f"{parts[0][0]}***@{parts[1]}"
```

**自动脱敏：**

### 9.2 模型调用安全

所有业务模型调用复用 `app/llm/service.py`、`router.py`、`gateway.py`，不自行复制闸门或直接连接云端SDK。公开内容按配置调用，内部内容需要获准精确主机，敏感内容禁止发送到云端，涉密内容拒绝AI处理；缺少合适私有模型时不得降级云端。

角色与权限决定可读资料；实际问题、会话历史、文档正文及来源决定模型内容等级。不能只按用户角色分级，也不能接受客户端自行降级。重写、向量化、重排及生成同样受边界约束；兼容配置开关不关闭安全检查。日志/审计不得保存密钥或敏感原文，完整审计覆盖仍是待完成目标。

学习推荐、提纲与纪要当前采用授权检索、模板、原文摘录，不调用外部模型。新增模型能力须登记、验证数据边界并同步测试与配置说明。

### 9.3 SQL 注入防护

**✅ 安全的做法（使用 ORM）：**

from sqlalchemy import select
from app.models import User

### 9.4 租户隔离（强制执行）

复用 `app/core/tenant.py` 的 ContextVar、`tenant_context`、`before_flush` 和 `do_orm_execute` 机制。租户来自登录态；写入注入/验证tenant_id，ORM查询追加租户条件。不要复制旧示例中不存在的 SQLAlchemy `before_query` 事件。

组织范围由 `app/services/org_scope.py` 及各业务服务再次过滤；公共政策共享不是任意跨租户写入权限。原生SQL、系统扫描和显式绕过路径必须限定目的和范围，不能假设ORM事件覆盖所有查询。后台任务按真实责任用户权限处理；缺少租户/组织时拒绝或跳过。安全回归覆盖跨租户、跨组织、空授权及来源权限变化。

```python
import logging
import json
from datetime import datetime

class JSONFormatter(logging.Formatter):
    """JSON 格式化器"""
    
    def format(self, record: logging.LogRecord) -> str:
        log_data = {
            "timestamp": datetime.utcnow().isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "module": record.module,
            "function": record.funcName,
            "line": record.lineno,
        }
        
        # 附加字段
        if hasattr(record, "user_id"):
            log_data["user_id"] = record.user_id
        if hasattr(record, "tenant_id"):
            log_data["tenant_id"] = record.tenant_id
        if hasattr(record, "trace_id"):
            log_data["trace_id"] = record.trace_id
        
        # 异常信息
        if record.exc_info:
            log_data["exception"] = self.formatException(record.exc_info)
        
        return json.dumps(log_data, ensure_ascii=False)
```

### 12.2 审查流程

以下为协作目标流程；当前仓库未提供CI/自动部署流水线文件，需手动执行相应检查并记录结果，不能宣称已有自动门禁。

```
1. 开发者提交 PR
   ↓
2. CI 自动检查（格式、测试、覆盖率）
   ↓
3. 至少 1 人审查代码
   ↓
4. 审查通过 + CI 通过 → 合并
   ↓
5. 按项目已配置流程执行测试环境部署（当前未提供自动部署流水线）
```

### 12.3 常见问题

| 问题 | 说明 | 解决 |
| --- | --- | --- |
| **硬编码** | 时限、权重写死在代码里 | 移到配置文件 |
| **God Class** | 一个类几千行 | 拆分职责 |
| **缺少异常处理** | 只写 happy path | 添加 try-except |
| **测试不充分** | 只测正常情况 | 补充异常和边界测试 |
| **日志太少** | 出问题无法排查 | 关键节点添加日志 |
| **注释过时** | 代码改了注释没改 | 同步更新注释 |

## 附录：工具与命令

运行配置以[运行指南](docs/RUNNING.md)为准，容器部署以[Docker指南](deploy/docker/README.md)为准，迁移以[迁移指南](migrations/README.md)为准。当前迁移头为 `012_member_self`；不存在 `scripts/init_data.py`，`scripts/init_db.py` 会删表，不能作为普通初始化或生产升级命令。

从项目根目录执行：

```bash
python -m pip install -r requirements-dev.txt
pre-commit install
python -m black --check app tests
python -m isort --check-only app tests
python -m flake8 app tests
python -m mypy app
python -m pytest tests/unit tests/security
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

实际格式工具配置以 `pyproject.toml` 和 `.pre-commit-config.yaml` 为准，不在本文复制另一份会漂移的配置。mypy配置依赖SQLAlchemy插件，历史环境因插件缺失未进入业务代码检查；未经新运行不能宣称类型检查已通过。测试日志和覆盖率写入 `tmp/test-results/`。

## 主分支与本地扩展的记录约定

主分支当前迁移头为 `012_member_self`；党员原件是私有数据，不进入知识库或模型。平台系统详情直接限定 `system_admin`，治理接口按实际权限、租户/组织过滤。待合入的本地 `auth_version` 和扩展工作台不能作为当前实现；未来迁移须沿主分支连续链设计。记录本地测试必须注明被测代码范围，不能将SQLite/模拟并发扩大为PostgreSQL锁竞争验收。
