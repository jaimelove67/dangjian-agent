# 待学校 / 组织部门确认清单

> 用途：把"代码已经做到门口、但规则得由学校定"的事项集中到一页纸上。每条写清**谁确认 → 确认什么（要具体到能签字的程度）→ 确认后系统立刻能做什么 → 现在卡在哪**。
> 编制：2026-10-17。收录 `docs/任务清单.md` 中状态为"⚠️ 部分实现 / 🔒 前置闸门 / ❌ 未实现"且**卡在外部输入**的事项（不含纯代码可做项，如 `T-SEC-07` 的访问日志与备份恢复机制、`T-NFR-03` 的向量库分级演进取舍、`T-MEM-03` 的公示登记与提醒读数改造）。
> 原则：**不编规则**。日历天数、时限、指标、敏感词表一律等确认后落 `config/business_rules.yaml` 并注释来源，不先写一个"看起来合理"的数字再让人来改。

## 逐项说明

### 1 电子记录合规性与效力

- **谁确认**：学校组织部门（会同信息化部门、保密管理部门）。
- **确认什么**：电子记录能否作为发展党员 / 组织生活的正式依据；哪些环节**必须**纸质原件；归档后能否修改、失效怎么算；多方审核意见怎么进发布清单。
- **确认后能做什么**：`T-GATE-01` 闭环后解锁归档 / 查历史 / 导出（现在按预期锁定），`T-ORG-08` 的归档与失效逻辑按结论落地，`T-SEC-12` 的审核意见进发布清单。
- **现在卡在哪**：系统已按"未确认即锁定"实现，属预期行为；涉及电子记录的业务（会议记录归档 `T-ORG-06`）在界面上写明"归档前经合规确认"。

### 2 敏感信息硬拦截规则清单

- **谁确认**：组织部门（业务口径）+ 保密管理部门（密级口径）。
- **确认什么**：哪些词 / 材料类型必须**硬拦截**、哪些只提示风险；政审类材料（现在默认涉密、正文不出网不进向量库）能否改用校内 / 本地模型处理；敏感件能否走公网模型。
- **确认后能做什么**：清单落 `config/business_rules.yaml` 的敏感规则（唯一来源 `app/rag/privacy.py`），`T-WF02-09` / `T-SEC-09` 一并闭环；现在只有"通用个人标识（身份证 / 手机号 / 邮箱等）+ 声明密级"这一层。
- **现在卡在哪**：规则只能**提高**等级，不能代替组织的完整保密审查——这一点已写进模块文档，不假装做到了。

### 3 公示环节口径（发展党员）

- **谁确认**：学校党委 / 组织部门。
- **确认什么**：① "公示不少于 5 个工作日"里的**工作日**怎么算（是否含法定节假日、寒暑假是否顺延）；② 公示起止日期由谁登记、公示范围（支部 / 院系 / 学校）；③ 公示期未满时系统只提示还是阻断支部大会决议的登记。
- **确认后能做什么**：新增"公示起止登记"并在公示期临近 / 届满时提醒（按确认口径算工作日），`T-MEM-03` 的"公示"节点补齐。
- **现在卡在哪**：全仓库里"公示"只作为材料要求（"公示情况报告"）与模板栏目存在，**没有起止日期可登记**，系统算不出公示是否满 5 个工作日。凭猜测起算日期做提醒，只会逼组织补一个假日期——所以宁可不做。

### 4 政审是否作为独立节点

- **谁确认**：学校党委 / 组织部门。
- **确认什么**：政审除了"政治审查材料"这份材料之外，是否还需要系统按节点提醒（例如函调发出后多久未回复提醒）；政审结论的登记口径。
- **确认后能做什么**：加政审节点提醒；或明确"只在材料与档案检查里体现"，把 `T-MEM-03` 的"政审"节点按此口径收口。
- **现在卡在哪**：政审当前只作为"发展对象 → 预备党员"的材料要求与 `T-MEM-12` 的密级口径存在，没有独立时间节点。

### 5 团组织推优与 28 周岁核对

- **谁确认**：学校党委 / 团委 / 组织部门。
- **确认什么**：细则要求"28 周岁以下青年入党一般应经团组织推优"，但**名册里没有出生年月**——是明确"由组织线下核对，系统只登记推优事实"，还是要求系统采集出生年月？
- **确认后能做什么**：若维持不采集（当前口径），界面上已明写"系统不判断年龄，请组织核对"，缺推优记录不阻断任何环节；若确认要采集，需同时确认出生年月的数据级别与可见范围（涉及 `T-MEM-12` 的分级口径）。
- **现在卡在哪**：`T-MEM-13` / `T-MEM-06` 已完成"只登记 + 提示"（`member_league_recommendations`，`age_notice` 明写请组织核对）。**系统不判断年龄、不新增出生年月字段**是刻意选择：加字段做校验等于要求组织为了过校验去编一个生日。

### 6 OCR 识别方式与图片件出校

- **谁确认**：信息化部门（技术方式）+ 保密管理部门（能否出校）。
- **确认什么**：用哪种识别方式（本地 / 校内 / 公网服务）、扫描件与图片件能否出校、识别失败时的人工兜底责任人。
- **确认后能做什么**：接入 OCR，`T-WF01-04` 从"给出替代路径"升级为"能解析扫描件"。
- **现在卡在哪**：图片件目前返回"未接入 OCR + 三条替代路径"的可执行提示；敏感件不得走公网识别是已定原则。

### 7 年度党建考核指标

- **谁确认**：学校党委 / 组织部门。
- **确认什么**：年度考核指标表——指标项、统计口径、分值 / 权重、数据来源、统计周期；以及本年度的指标版本。
- **确认后能做什么**：按版本录入 `T-ASM-01` 指标，自动归集组织生活 / 党员发展 / 学习教育数据并出缺项与佐证（`T-ASM-02`~`T-ASM-07` 已就绪）。
- **现在卡在哪**：现在只有可配置的指标框架与通用归集，**不编学校指标**（编一套看起来合理的指标，等于让学校按错口径准备材料）。

### 8 评测样本与专家复核

- **谁确认**：组织部门（组织党建专家逐题复核）+ 信息化部门（压测环境与并发口径）。
- **确认什么**：问答 200 / 拒答 30 / 时效 20 的样本从哪些真实业务场景来；谁做专家答案复核；压测的并发数与可接受响应时间。
- **确认后能做什么**：`T-QA-EV-01` / `T-QA-EV-02` 达标后出评测报告，`T-MILE-03`（老师试用）有前置条件；`T-NFR-01` / `T-QA-EV-03` 有验收基线。
- **现在卡在哪**：当前样本（问答 20 / 拒答 6 / 时效 0）远未达标，且**关键词命中不计入**专家复核——不能拿"命中率"宣称问答效果已确认。这两个任务**不允许用代码伪造样本或专家结论**。

### 9 性能与容量的可接受口径

- **谁确认**：信息化部门。
- **确认什么**：并发用户数、单次问答的可接受响应时间（分位数）、向量检索的扩容方式（`pgvector` 是否够用、是否需要 `Qdrant` / `Milvus`）。
- **确认后能做什么**：负载测试有明确的通过 / 不通过判据；`T-NFR-03` 的存储层分级演进按同一口径定取舍。
- **现在卡在哪**：不先编一个"3 秒"当验收线——数字得由学校认可。

### 10 私有化 / 隔离部署环境

- **谁确认**：信息化部门。
- **确认什么**：部署位置（内网 / 隔离网）、域名与证书、数据库与文件存储位置、出网策略（哪些调用允许出公网）。
- **确认后能做什么**：生产容器构建与部署验收（`T-NFR-06`），对象存储或校内存储接入（`T-INFRA-03`）。
- **现在卡在哪**：开发环境（Docker Compose）可跑，原件当前为**本地认证加密文件存储**，未接对象存储。

### 11 备份恢复与数据删除流程

- **谁确认**：信息化部门（技术流程）+ 组织部门（删除的审批与范围）。
- **确认什么**：备份频率与保留期、恢复演练的责任人与频次、数据删除的审批链与删除范围（是否含审计日志、留痕如何保留）。
- **确认后能做什么**：`T-NFR-07` 的"演练可执行 + 删除留痕"闭环（与 `T-SEC-07` 的备份恢复 / 数据删除机制配套）。
- **现在卡在哪**：备份与恢复机制可执行但**未在学校的保留期与责任人下验收**；审计已全量记录（`T-INFRA-06`、`T-SYS-05`）。

### 12 静态加密与密钥托管

- **谁确认**：信息化部门 + 保密管理部门。
- **确认什么**：数据库 / 文件 / 备份的加密方式与算法要求、密钥由谁托管与轮换、审计缓冲文件的密钥保管。
- **确认后能做什么**：`T-SEC-06` 配置生效并验收。
- **现在卡在哪**：已有本地认证加密文件存储与审计缓冲（同一机制），但"静态加密配置生效"的验收标准要按学校要求定。

### 13 多租户验收范围

- **谁确认**：学校（是否需要真正的多学校租户共存）。
- **确认什么**：是面向**一个学校**（多院系 / 多支部）还是**多学校**共用一套部署；若是后者，跨租户的运维、备份、审核责任人是谁。
- **确认后能做什么**：`T-SEC-03` 按确认范围加固与验收（现在的隔离已按租户维度做，跨租户请求被拒绝）。
- **现在卡在哪**：范围不明确时，做"更强的多租户"可能是在解决一个不存在的问题。

### 14 里程碑评审与老师试用

- **谁确认**：学校项目负责人（组织者）。
- **确认什么**：M0′ 需求与现状评审的时间与参加人（含本清单的逐条确认）、老师试用的范围与时间、试用反馈的闭环责任人。
- **确认后能做什么**：`T-MILE-01`~`T-MILE-04` 推进，`T-MILE-02`（MVP 验收）逐项确认。
- **现在卡在哪**：这些里程碑的验收动作本身就是"人来评审 / 试用"，代码无法单方面完成。

## 用法建议

1. **一次会议过一遍**：本清单 14 条按"谁确认"分组，同一部门的事项合并成一次确认，避免来回找人。
2. **确认结论落在配置里**：能变成配置的（时限、指标、敏感词、公示天数）写进 `config/business_rules.yaml` 并注释来源与日期；不能变成配置的（合规结论、审核意见）写进本文件下方的"确认结论"小节。
3. **不要为了过验收编数据**：样本、专家结论、指标数字、出生年月、工作日日历——这些一旦编出来，系统看起来更完整，但学校会按错的口径准备材料。
