# 党建工作智能体 · 项目讲解与演示手册

> 用途：对外讲解 / 培训 / 演示。全套演示在**测试租户「测试大学」（TEST_TENANT）**上进行，不涉及任何真实学校数据。
> 编写日期：2026-10-17（所有账号、数据条数、表结构均取自当前运行环境实测）
> 演示地址：前端 `http://127.0.0.1:5666`，后端 `http://127.0.0.1:18000`

---

## 第 1 章　项目是什么

### 1.1 一句话定位

**面向高校党建业务的 AI 辅助工作台**：把制度问答、知识库、党员发展、组织生活、中心组学习、年度考核、党员自助等分散的业务，收进同一套按「角色 × 所属组织」隔离的系统里，AI 负责检索、起草、给建议，**业务结论一律由组织人员人工确认**。

### 1.2 解决什么问题

| 原来的痛点 | 系统怎么做 |
| --- | --- |
| 制度文件散在各处，新人问不到 | 知识库统一上传、切分、向量化，问答带引用出处，无依据明确拒答 |
| 党员发展靠 Excel 和纸质台账，阶段靠人记 | 名册 + 批次 + 材料 + 阶段流转 + 民主投票全流程留痕 |
| 三会一课、中心组学习记录难追溯 | 计划 → 落实 → 纪要 → 审核 → 归档，每一步有版本与审核人 |
| 年度考核靠手工收材料 | 指标 → 任务 → 佐证关联 → 提醒 → 人工审核 → 目录导出 |
| 党员看不到自己的档案、交材料靠跑腿 | 本人档案只读 + 私有材料在线提交（不进知识库、不送模型） |
| 谁改了什么说不清 | 全量审计日志 + 内容修订版本，只追加不覆盖 |

### 1.3 技术栈

| 层 | 选型 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite（dev 端口 5666） |
| 后端 | FastAPI + SQLAlchemy 2.0（async）+ Alembic |
| 数据库 | PostgreSQL 16 + **pgvector**（向量检索） |
| 缓存/队列 | Redis（会话、任务、幂等） |
| AI 编排 | LangChain + LangGraph |
| 模型（百炼 DashScope） | 生成 `qwen3.8-flash`；向量 `qwen3.7-text-embedding-flash`（1024 维）；重排 `qwen3.7-text-rerank` |
| 部署 | Docker Compose（postgres + redis + app + nginx 前端） |

### 1.4 目录结构

```text
app/           后端：api / models / services / rag / chains / llm / rules / core
frontend/      正式业务前端（Vue 3）
config/        模型路由、业务规则、检索策略、学习模板
migrations/    数据库迁移（当前迁移头 012_member_self）
tests/         单元、集成、安全测试与评测样本
scripts/       启动、安装、辅助检查
deploy/        容器部署与运维
docs/          指南、设计与归档文档
```

后端按业务纵向切分：`api/v1/` 下每个模块一个文件（auth、admin、governance、knowledge、qa、member 系列、meeting、study、assessment、notifications、health），`services/` 对应业务服务层，`models/` 对应数据表。

### 1.5 九大功能模块

| # | 模块 | 入口 | 一句话 |
| --- | --- | --- | --- |
| 1 | 制度问答 | `/ask` | 基于本校知识库作答，带引用；无依据明确拒答 |
| 2 | 知识库 | `/knowledge` | 上传/切分/向量化/复核/审核/入库/废止，分四级可见范围 |
| 3 | 党员发展 | `/members` | 名册、批次、材料、阶段流转、民主评议、组织关系接转、上级报送 |
| 4 | 组织生活 | `/meeting` | 三会一课与主题党日：计划 → 落实 → 纪要审核 → 归档 |
| 5 | 中心组学习 | `/study` | 年度计划 → 每期安排 → 纪要审核 → 归档（仅学校/院系管理员） |
| 6 | 年度考核 | `/assessment` | 指标 → 任务 → 佐证 → 人工审核 → 提醒 → 目录导出 |
| 7 | 党员自助 | `/my-archive`、`/my-materials` | 本人档案只读、私有材料提交 |
| 8 | 账号与治理 | `/accounts`、`/governance` | 开户、组织树、租户、人工审核、审计查询 |
| 9 | 系统状态 | `/system` | 依赖就绪详情（仅平台管理员） |

### 1.6 三条设计底线（讲解时重点强调）

1. **AI 只辅助，不下结论**：阶段认定、归档效力、考核结果全部人工完成；系统给"建议"和"待人工确认事项"，明确标注不构成组织认定。
2. **默认最严**：电子归档默认关闭、外部通知默认不投递、涉密内容禁止出网、申请人可见范围最窄。
3. **只追加不覆盖**：内容修订、审核证据、审计日志、阶段历史一律追加版本，历史可追溯。

## 第 2 章　角色体系（7 类）

### 2.1 角色总表

数据范围逐级包含：**本人 < 支部 < 院系 < 学校 < 平台**。

| 角色 | 代码 | 数据范围 | 开户时必须绑定的组织 | 说明 |
| --- | --- | --- | --- | --- |
| 平台系统管理员 | `system_admin` | 平台（跨校） | 不绑定学校 | 开户、登记租户、系统状态；**看不到任何学校业务数据** |
| 学校管理员 | `school_admin` | 全校 | 学校 | 全校业务总负责 |
| 院系管理员 | `department_admin` | 本院系（含支部） | 院系 | 本院系业务 |
| 支部书记 | `branch_secretary` | 本支部 | 支部 | 支部日常主操作者 |
| 组织员 | `organizer` | 本支部 | 支部 | 协助支部业务 |
| 普通党员 | `member` | 本人 | 支部 | 自助 |
| 申请人 | `applicant` | 本人 | 支部 | 自助（制度目录仅公开级） |

### 2.2 菜单权限对照（✓ 可见，— 不可见）

| --- | --- | --- | --- | --- | --- | --- | --- |

| 知识库 `/knowledge` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓只读 | ✓只读 |
| 党员发展 `/members` | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| 组织生活 `/meeting` | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| 中心组学习 `/study` | ✓ | ✓ | ✓ | — | — | — | — |
| 年度考核 `/assessment` | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| 管理与审核 `/governance` | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| 创建账号 `/accounts` | ✓ | — | — | — | — | — | — |

### 2.3 讲解时常被追问的三个细节

- **中心组学习只有学校管理员和院系管理员有**（`study.query` 权限），支部书记看不到该菜单——这是设计，不是 bug。
- **支部书记和组织员的唯一差别**：支部书记多一项考核归集的人工审核权（`assessment.review`）。
- **平台与学校管理员看不到「本人档案/个人材料」菜单**（权限集合里不含 `member.self_query`、`member.material_submit`），自助功能是党员与申请人专属。

### 2.4 制度可见范围（四级）

| 角色 | 能看到 |
| --- | --- |
| 学校管理员 | 公开 + 学校 |
| 院系管理员 | 公开 + 学校 + 院系 |
| 支部书记 / 组织员 | 公开 + 学校 + 院系 + 支部 |
| 普通党员 | 公开 + 学校 |
| 申请人 | **仅公开**（所以目录常为空，这是需求规定） |

## 第 3 章　数据库全表介绍（35 张）

全部表在 PostgreSQL `public` schema 下。**共性字段**（除非特别说明）：`id`、`tenant_id`（租户隔离）、`created_at`、`updated_at`、`is_deleted`（软删除，所有删除都是逻辑删除）。

### 3.1 租户、组织与账号（3 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `tenants` | 租户（平台 → 学校），多级树 | `tenant_id`、`name`、`tenant_type`、`parent_id`、`path`、`config`、`contact_*`、`config_version` |
| `org_units` | 组织单元：学校 / 院系 / 支部 | `name`、`org_type`、`parent_id`、`path`、`leader_name`、`leader_phone`、`is_active` |
| `users` | 登录账号 | `username`、`name`、`password_hash`、`role`、`org_unit_id`、`tenant_id`、`is_active` |

> 层级硬规则：**学校**无上级且同租户唯一；**院系**上级是学校；**支部**上级是学校或院系。开户时角色与组织类型必须匹配，否则 422。

### 3.2 知识库与问答（3 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `knowledge_docs` | 制度文件主表 | `doc_id`、`title`、`issuer`、`doc_number`、`level`、`visibility`、`security_level`、`effective_date`、`expiration_date`、`status`、`authority`、`validity`、`review_status`、`next_review_at`、`search_vector` |
| `embedding_chunks` | 切分后的片段与向量 | `doc_id`、`chunk_id`、`content`、`sequence`、`article`、`embedding`（vector）、`metadata` |
| `qa_sessions` | 问答会话与结果 | `user_id`、`question`、`answer`、`citations`、`has_sufficient_evidence`、`retrieved_count`、`used_count`、`refused`、`warnings`、`disclaimer`、`versions` |

> `refused=true` 表示**依据不足已拒答**——这是系统的核心安全行为，讲解时务必提。

### 3.3 党员发展（13 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `member_profiles` | 培养对象名册 | `name`、`org_unit_id`、`current_stage`、`stage_joined_on`、`materials`、`pending`、`year`、`batch_no`、`user_id`、`relation_status` |
| `member_batches` | 年度发展批次 | `year`、`batch_no`、`label`、`org_unit_id` |
| `member_materials` | 材料记录（含党员自助提交） | `profile_id`、`stage`、`material_type`、`file_version`、`submit_date`、`review_status`、`submission_key`（幂等）、`content_sha256`、`user_id`、`data_level` |
| `member_stage_history` | **人工**阶段流转历史 | `profile_id`、`from_stage`、`to_stage`、`decision_date`、`basis`、`opinion`、`decided_by` |
| `member_selections` | 支部拟推荐名单（选优结论） | `batch_no`、`round_no`、`target_stage`、`candidates`、`basis`、`research_on`、`review_status` |
| `member_league_recommendations` | 团组织推优台账 | `profile_id`、`league_org`、`recommended_on`、`revoked_on`、`stage` |
| `member_votes` | 多轮选优投票 | `batch_no`、`round_no`、`profile_id`、`voter_id`、`vote`、`comment` |
| `member_reviews` | 民主评议党员结果（年度 × 党员） | `year`、`procedure`、`grade`、`basis`、`rectification`、`review_status` |
| `member_cultivation` | 培养与表现数据 | `category`、`score`、`period`、`verified_by`、`is_risk`、`risk_note` |
| `member_reminders` | 关键节点提醒台账 | `kind`、`due_on`、`status`、`processed_by`、`processed_at` |
| `member_transfers` | 组织关系接转（转入/转出与介绍信） | `direction`、`counterpart_org`、`letter_no`、`issued_on`、`valid_until`、`status`、`receipt_no`、`revoked_on` |
| `member_upper_reports` | 上级审批/备案报送台账 | `item`、`kind`、`upper_org`、`letter_no`、`submitted_on`、`status`、`result`、`reply_no` |
| `member_archive_checks` | 档案检查结果（仅提示） | `profile_id`、`checked_at`、`rule_version`、`result` |

### 3.4 组织生活（2 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `meeting_records` | 一次活动一条记录，修订只追加版本 | `org_unit_id`、`activity_type`、`title`、`scheduled_on`、`held_on`、`host`、`participants`、`transcript`、`minutes`、`revision`、`review_status`、`archived_at`、`archive_policy_version` |
| `meeting_tasks` | 会议任务台账 | `record_id`、`task_text`、`owner_name`、`due_on`、`status`、`confirmed_by`、`handled_at` |

### 3.5 中心组学习（2 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `study_plans` | 年度计划（每组织每年一份，修订留版本） | `org_unit_id`、`year`、`title`、`priorities`、`source_doc_ids`、`responsible`、`revision`、`review_status` |
| `study_plan_items` | 每期学习安排 | `plan_id`、`topic`、`scheduled_on`、`responsible`、`agenda`、`outline`、`meeting_record_id` |

### 3.6 年度考核（8 张）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `assessment_indicators` | 考核指标（追加版本，不覆盖） | `school_org_id`、`year`、`code`、`version`、`name`、`requirement`、`formula`、`target`、`required_evidence`、`confirmed` |
| `assessment_tasks` | 人工年度任务 | `org_unit_id`、`indicator_code`、`owner_id`、`due_date`、`declared_progress`、`manual_value`、`basis`、`review_status` |
| `assessment_evidence` | 指标 ↔ 真实知识文档版本的链接（**不复制伪造材料**） | `doc_id`、`source_version`、`revision`、`review_status` |
| `assessment_plans` | 学院/支部计划（修订追加新版本并清除审核态） | `org_unit_id`、`year`、`version`、`content`、`review_status` |
| `assessment_runs` | 可复算的计算快照（同输入复用同结果） | `fingerprint`、`engine_version`、`inputs`、`results`、`review_status` |
| `assessment_reminders` | 考核提醒与处理记录（去重，不重复外发） | `task_id`、`kind`、`dedup_key`、`status`、`handled_by` |
| `assessment_archives` | 审核后归档目录快照 | `run_id`、`policy_version`、`manifest` |
| `assessment_policies` | 学校考核配置（**电子归档默认关闭**） | `archive_enabled`、`reminder_advance_days`、`confirmed_by`、`confirmation_note` |

### 3.7 治理、审计与平台（6 张 + 1 张迁移）

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `audit_logs` | 审计日志，**只追加不修改** | `user_id`、`user_name`、`action`、`resource_type`、`resource_id`、`data_level`、`ip_address`、`request_id`、`result`、`old_value`、`new_value` |
| `human_reviews` | 人工审核台账 | `source_kind`、`source_id`、`source_version`、`snapshot`、`status`、`submitted_by`、`reviewed_by`、`opinion` |
| `content_revisions` | 业务修订与审核证据（只追加） | `resource_type`、`resource_id`、`revision`、`action`、`actor_id`、`reason`、`snapshot` |
| `config_revisions` | 配置变更版本 | `version`、`actor_id`、`reason`、`values` |
| `durable_jobs` | 可持久任务（重试/租约/去重） | `kind`、`dedup_key`、`status`、`attempts`、`available_at`、`lease_until`、`error_code` |
| `model_usage` | 模型调用记录 | `model_type`、`model_name`、`result`、`duration_seconds`、`retrieval_score`、`error_code` |
| `notification_deliveries` | 「事件 × 渠道 × 接收人」投递记录（同去重键只一行） | `event`、`dedup_key`、`channel`、`recipient_id`、`status`、`attempts`、`last_error` |
| `alembic_version` | 迁移版本 | `version_num` |

## 第 5 章　分角色演示步骤

### 5.1 平台系统管理员 `admin`

**登录**：`admin` / `Test123456`（左侧菜单出现「创建账号」「系统状态」「管理与审核」）

| 步 | 操作 | 预期 |
| --- | --- | --- |
| 1 | 管理与审核 → 组织与账号，看「管理租户」下拉 | 可切换 PLATFORM_TENANT / 测试大学 / 其他学校 |
| 2 | 切到「测试大学」→ 看组织目录 | 显示测试大学党委 / 计算机学院党委 / 本科生第一党支部三行 |
| 3 | 点「新增组织」 | ⚠️ 弹窗里**组织类型默认是「院系」**，演示时故意不改 → 提交 → 报 `422 父组织必须同租户且类型正确`（这是设计好的讲解点） |
| 4 | 改类型为「学校」再提交 | 报 `422 同租户只能有一个学校根组织`（测试大学已有根组织） |
| 5 | 改类型为「院系」、上级选「测试大学党委」 | 创建成功，表格新增一行 |

**讲解要点**：平台账号**看不到任何学校的名册和业务数据**——用它打开「党员发展」会提示无权，这正好演示租户隔离。

### 5.2 学校管理员 `test-reviewer`

**登录**：`test-reviewer` / `Test123456`（菜单最全，无中心组以外的限制）

| 步 | 操作 | 预期 |
| --- | --- | --- |
| 1 | 制度问答 → 问一个知识库里有的制度问题 | 返回带引用出处的答案，可点开引用看原文 |
| 2 | 再问一个知识库里没有的问题 | **明确拒答**（展示"不编造"这条底线），对应 `qa_sessions.refused=true` |
| 3 | 知识库 → 看 14 份文档 → 点开一行 | 详情面板可下载原件、看处理状态、改元数据 |
| 4 | 上传一份测试制度文件 → 点「处理待检索片段」 | 状态从"待处理"变"已处理"（会调用云端向量模型，产生费用） |

**验证点**：`select count(*) from member_stage_history;` 增加一条；`qa_sessions` 新增一行。

## 第 6 章　一条主线串讲（建议的讲解顺序）

按下面顺序讲一遍，听众就能理解系统是"怎么流转"的：

| 顺序 | 环节 | 用哪个账号 | 关键话术 |
| --- | --- | --- | --- |
| ① | 建租户与组织树 | `admin` | "先有组织，才有账号和数据范围" |
| ② | 开账号 | `admin` | "角色必须和组织类型对上，否则 422" |
| ③ | 上传制度并向量化 | `test-reviewer` | "没有制度，问答一律拒答——这是安全设计" |
| ④ | 制度问答 | 任意 | "带引用、可溯源、无依据不编造" |
| ⑤ | 登记名册 → 推优 → 材料 → 阶段流转 | `branch-secretary` | "每一步都要人工确认，系统只给建议" |
| ⑥ | 民主评议与投票 | `branch-secretary` | "程序与等次由人工记录，系统如实留存" |
| ⑦ | 组织生活：计划 → 落实 → 纪要审核 → 归档 | `branch-secretary` + 他人审核 | "登记人与审核人不能是同一人" |
| ⑧ | 考核：指标 → 任务 → 佐证 → 审核 → 导出 | `test-reviewer` → `test-dept` → `branch-secretary` | "佐证只做链接，不复制伪造材料" |
| ⑨ | 党员自助 | `test-member` | "私有材料不进知识库、不送模型" |
| ⑩ | 审计与追溯 | `admin` | "所有关键操作只追加不修改" |

## 第 7 章　讲解时最常被问的 8 个问题

| 问题 | 标准回答 |
| --- | --- |
| AI 会自动认定党员阶段吗？ | 不会。系统只给"流转建议"与"待人工确认事项"，阶段流转必须人工执行并记入 `member_stage_history`。 |
| 为什么有些问题拒答？ | 知识库没有依据就明确拒答（`refused=true`），不编造。先上传制度文件并完成向量化。 |
| 为什么我看不到某个菜单？ | 菜单由角色权限决定。典型：中心组学习只有学校/院系管理员有；自助功能只有党员/申请人有。 |
| 为什么我的知识库是空的？ | 申请人的可见范围仅公开级；其他角色看空态说明，确认自己的可见范围。 |
| 电子归档有法律效力吗？ | 默认关闭。需学校先做"电子记录效力确认"并登记依据，之后归档才具备约定效力。 |
| 数据会发给大模型吗？ | 受出网白名单控制；敏感与涉密内容一律拦截。党员私有材料不进知识库、不送模型。 |
| 误操作能撤回吗？ | 删除都是软删除（`is_deleted`）；内容修改走版本追加（`content_revisions`）；审计日志只追加。 |
| 能对接企业微信/邮件通知吗？ | 通知走"事件 → 渠道"链路，出厂只有站内渠道 `inapp`，默认不投递任何外部消息；外部渠道按同一协议登记即可接入。 |

## 附录 A　演示前 5 分钟检查清单

1. `curl http://127.0.0.1:18000/api/v1/health/ready` → 200。

## 附录 B　已知会踩的坑（演示时提前规避）

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 新增组织默认类型 | 弹窗默认「院系」，建学校根组织必 422 | 手动改成「学校」 |
| 登记租户后不切换 | 后续操作落在原租户 | 顶部「管理租户」手动切 |
| 后端改代码不生效 | 没开热重载 | 手动重启 uvicorn |
| 前端代理端口错 | 接口全 404/超时 | `VITE_API_TARGET` 指向 18000 |
| 自审自 | 提交与审核同一账号被拒 | 演示时两个账号交替操作 |
| 知识库未向量化 | 问答全部拒答 | 先点「处理待检索片段」 |
