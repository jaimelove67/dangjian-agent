## 已确认的主要问题与修复方向

P1 表示阻断核心使用或违反安全/溯源约束；P2 表示影响完整性、运行维护或后续使用。以下按实际影响排序，未将尚未进入开发阶段的 M5/M6 功能当作运行时 bug。

### P1：数据分级与敏感访问边界可被绕过

[qa.py:83](<../../../app/api/v1/qa.py:83>) 直接使用请求中的 `data_level`，非法值和 `classified` 回退成 `public`；未采用鉴权依赖已推导的角色数据级别。普通党员合成探针中，角色级别是 `internal`，提交 `public`、`sensitive`、`classified` 得到的实际 RAG 级别分别为 `public`、`sensitive`、`public`。

当前本地 `ENABLE_DATA_LEVEL_GATEWAY=false`，闸门关闭时直接放行。[gateway.py:57](<../../../app/llm/gateway.py:57>)。4 项安全测试由此失败；仅在测试进程启用开关后恢复通过。正式检索还未强制携带角色可见范围和文档密级限制。

修复方向：由服务端依据账号授权与被检索文档的实际密级确定访问及模型路由，拒绝无效分级，强制敏感/涉密边界；保证向量化、重排的本地约束。该问题已用合成数据复现；本次没有观察或触发真实公网数据外发。

### P1：上传接口在校验阶段必然报错

[knowledge.py:85](<../../../app/api/v1/knowledge.py:85>) 引用未定义的 `settings.MAX_UPLOAD_SIZE`，真实小文件上传返回 500，日志明确为 `AttributeError`。该文件错误处理分支还使用未声明的 `logger`（第 140 行），修复上传大小后遇到落库异常仍会掩盖原始错误。

修复方向：补齐一致的上传大小配置与日志声明，再验证合法文件、超限文件、非法元数据及落库失败路径。

### P1：当前数据库未完成核心迁移

只读检查确认仅有 `users` 表；缺少 `tenants`、`org_units`、`knowledge_docs`、`embedding_chunks`、`audit_logs`、`alembic_version`。没有 `chinese_zh`、`pg_trgm` 和相关索引。文档查询实际报 `relation "knowledge_docs" does not exist`。已有数据库集成测试 5 项失败。

修复方向：制定保留现有 `users` 数据的迁移方案，完成核心表和检索配置，并以数据库集成测试复核。当前数据库与 Alembic 管理状态不一致，恢复步骤需要兼顾已有表。

### P1：模型没有在应用启动中注册，配置路由也忽略模型类型

[main.py:46](<../../../app/main.py:46>) 仍为加载模型 TODO；`init_models()` 仅在单独脚本入口执行。当前 DashScope Key 未配置、DashScope SDK 未安装，也未注册本地替代模型。真实问答首先报 `No available model ... ModelType.EMBEDDING`。

此外，[router.py:92](<../../../app/llm/router.py:92>) 的配置路由只有“分级 + 任务”，忽略 `model_type`。合成探针同时注册 LLM 与 Embedding 后，请求 Embedding 仍获得 LLM；初始化脚本的公开问答路由会产生此冲突，向量化与重排不能可靠选择各自模型。

修复方向：在生命周期初始化模型并验证必需模型就绪，统一模型配置来源，让路由匹配任务和能力类型；完善检索依赖故障的明确错误响应。

### P1：入库和检索使用不同文档关联键

[knowledge_service.py:140](<../../../app/services/knowledge_service.py:140>) 把 `document.id` 写入片段的 `doc_id`。但 [vector.py:94](<../../../app/rag/retrieval/vector.py:94>) 和 [keyword.py:90](<../../../app/rag/retrieval/keyword.py:90>) 都连接到 `KnowledgeDoc.doc_id`（用户填写的业务编号）。合成入库实际得到“片段存数据库主键，检索连接业务编号”。即使数据库和模型恢复，通常也检索不到刚上传的文档。

修复方向：统一存储关联键、检索 join 和按文档向量化时的编号解析；验证上传后同一文档确实能召回。

### P1：正式 RAG 未实现生成前拒答及引用核验

[rag_service.py:162](<../../../app/rag/rag_service.py:162>) 先调用生成，之后才判断分数充分性。分数为 0.1 的探针仍生成实质性答案；分数为 0.9、模型返回不存在的 `[99]` 时，错误引用原样返回且依据充分性标记为真。引用列表是从候选片段直接构造的，没有核验模型答案实际引用。

独立 [qa_chain.py:114](<../../../app/chains/qa_chain.py:114>) 已有生成前拒答、核验和会话处理，但正式 API 使用另一套 `RAGService`。响应也缺少文档要求的风险列表及服务端免责声明。

修复方向：统一正式问答链，将生成前阈值判断、真实引用核验、完整响应和会话接入同一条实际路径。新增测试应经过正式 API，避免只验证未使用的组件。

### P1：实际检索缺角色可见范围、时效和公共库并集

[qa.py:95](<../../../app/api/v1/qa.py:95>) 仅传租户和 `effective` 状态；检索器虽然支持可选 `security_level`，实际 API 没有提供该过滤。生成 SQL 的 WHERE 没有 `visibility`、`security_level`、生效/失效日期条件，也没有公共库并集。

影响：同租户下的组织/密级范围没有按文档落实；状态仍为有效但日期过期的文件不能按默认策略排除；共享公共库不能按设计命中。现有 ORM 租户过滤是有效的基础机制，但不能替代这些条件。

修复方向：在检索能力层强制注入授权范围、密级、日期和公共库策略，并用实际库中的公共、私有、过期及越权文件验证。

### P1：审计与人工审核没有接入完整业务流程

[core/audit.py:92](<../../../app/core/audit.py:92>) 提供只追加审计组件，但正式 API 未调用 `write_audit`；状态维护仅写普通日志。没有文档要求的审计查询、审核队列、审核人/时间与审核状态处理。

修复方向：把业务动作及生成建议接入持久审计和所需审核流程，再验证决策依据、变更前后值和查询能力。当前组件存在不能代表全量关键操作可追溯。

### P2：前端刷新令牌失败，退出没有服务端吊销

[auth.ts:15](<../../../frontend/src/api/auth.ts:15>) 设置刷新令牌后，[http.ts:90](<../../../frontend/src/api/http.ts:90>) 无条件用访问令牌覆盖 Authorization。真实浏览器调用此函数得到 401，并清除本地令牌；正确刷新令牌直接调用后端则为 200。

[auth.py:163](<../../../app/api/v1/auth.py:163>) 的退出只返回成功；本次测试令牌退出后继续查询用户仍为 200。

修复方向：保留调用者显式设置的 Authorization，补齐刷新生命周期及服务端退出吊销语义。自然等待令牌过期的完整流程未测试。

### P2：列表与人员管理仍是示例展示

[KnowledgeView.vue:51](<../../../frontend/src/views/KnowledgeView.vue:51>) 和 [MembersView.vue:82](<../../../frontend/src/views/MembersView.vue:82>) 加载固定示例数据。页面已明确标注示例，这是正确的呈现方式，但缺少后端列表、人员实体和状态持久化。上传成功后前端即使临时插入列表，刷新页面也不能从数据库恢复真实列表。

修复方向：先补查询与人员业务接口，再替换示例数据；保留现有建议接口的人工决策边界。

### P2：部署及快速启动包与当前工程不一致

- `scripts/start-all.bat:38` 和 `.sh:40` 指向不存在的 `frontend/apps/web-antd`，并调用 `pnpm dev`；正式工程实际为 `frontend/`、使用 npm。
- Compose 中 `DATABASE_URL` 使用同步 PostgreSQL 默认驱动，`app/db/session.py` 则要求异步引擎；本地检查该 URL 对应 dialect 的 `is_async=False`。

## 测试失败的归因与未验证范围

10 项原始失败的归因已区分：数据库相关 5 项属于当前环境未迁移；安全相关 4 项属于当前关闭闸门的配置及其放行行为；`test_health_check` 1 项使用 `MagicMock` 模拟实际异步的 `health_check_all`，应改用异步 mock，不能直接认定生产模型健康检查代码有同样错误。PDF 解析测试因缺 `pypdf` 跳过。

本机 Python 3.13.9，与文档建议 3.11/3.12 不同；FastAPI、SQLAlchemy、LangGraph 等已安装版本也不同于锁定的 requirements。上述测试真实运行于当前环境，不等于证明锁定版本下的干净安装和生产兼容性。

未验证：真实成功的上传/向量化/带引用问答、真实知识数据质量、实际多租户多组织越权场景、公网/本地模型生成、已有文档状态更新成功流程、生产容器构建部署、备份恢复、负载/性能及模型回答正确率。当前缺少必要表和模型，无法把这些项目计为通过。

反向审查没有将“未发现出网事件”解释为“出网安全已验收”，也没有将未接入 API 的组件测试通过解释为业务闭环完成。
