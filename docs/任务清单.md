## 0 使用说明

### 0.1 字段含义

每条任务采用统一字段：

```
- [ ] T-<模块>-<序号> | 任务名 | <优先级> | <实现状态>
      来源：FR/SEC/NFR/WF 编号
      依赖：任务 ID
      验收：可验证的完成标准
```

### 0.4 状态标记（与实现状态统一口径）

> 勾选框是 0.5「实现状态」的视觉速记，二者必须一致，不得各写一套。
> **勾选 ≠ 已通过业务验收**：验收结论以 §11.3 验收表、§1.10 必交付项对照和附录 C 里程碑为准。

| 标记 | 对应实现状态 | 含义 |
| --- | --- | --- |
| `[x]` | ✅ 已实现 | 当前工作区已有对应代码，任务转为**验收 / 加固** |
| `[~]` | ⚠️ 部分实现 | 部分完成或有明确边界未闭环 |
| `[ ]` | ❌ 未实现 / 🔒 前置闸门 | 需开发，或依赖外部确认未闭环 |

### 0.5 实现状态（校准列）

| 标记 | 含义 |
| --- | --- |
| ✅ 已实现 | 当前工作区已有对应代码，任务转为**验收 / 加固** |

### 2026-10-16（工作流运行日志查看 T-SYS-06E）

- 问题：`T-SYS-06` 里只剩"工作流运行日志查看"没做——任务台账只回答"我提交的任务现在什么状态"，`/admin/operations` 只给 24 小时聚合计数。运维真正要回答的是"这个租户最近跑了什么、卡在哪一步、失败是秒挂还是跑到超时"，此前只能翻服务端日志或直接查库。任务失败后界面只有一句"失败记录已保存，请联系管理员核对"，没有第几次、错误类型、耗时，排障等于从零开始。
- 为什么**不新建**运行日志表 / 迁移：任务队列的每次入队（`job_enqueue`）、每次尝试失败（`job_attempt_failed`）、每次完成（`job_completed`），加上三处定时扫描（`member_scheduled_scan` / `assessment_scheduled_scan` / `assessment_reminders_scan`）本来就已经写进审计。再建一张表就是把同一事实写两遍，还会多出"两张表不一致时信谁"的问题。交付的是**读模型**：`app/services/run_log_service.py`（纯查询构造 + `RunLogRow` 行映射，可单测）＋ `GET /admin/run-logs`（权限 `admin.ops`，即「运行审计」标签那一枚；租户内可见、跨租户不可见）。
- 事件清单只有一处：`RUN_EVENTS`（动作名 → 中文阶段名）既驱动查询收窄，也经 `event_text` 给界面直接用，前端不再翻译一遍。支持按事件 / 任务类型 / 结果 / 时间范围筛选分页；未知事件或任务类型返回 422 并说明，不静默给空结果（空结果会被误读成"没跑过"）。
- 入队事件也要能看出任务类型：`job_enqueue` 走 `audit_operation`，`new_value` 按仓库统一摘要口径只留 sha256 与字节数，拿不到明文类型。解法不是在共享脱敏逻辑上开口子，而是按 `resource_id` 批量补一次任务表（一次查询覆盖当前页，不做 N+1）；任务记录已清理时留空，不编造。任务类型筛选同样按**任务表**口径（`DurableJob.kind`）：定时扫描是调度器行为、不属于某一条任务，按类型筛时不出现（用事件筛"党员提醒扫描"可单独看）。
- 耗时（`duration_ms`）是本次新增的关键字段：`run_once()` 在 `asyncio.wait_for` 外层实测尝试耗时、`execute()` 实测执行耗时，成功与失败都写入审计——排障要能区分"秒挂"（权限 403、文档失效 404）和"跑到超时"（默认 120 秒上限）。领取时发现租约已耗尽、**没有真正执行**的尝试不写数字，界面显示"—"（改动前写入的旧记录同样显示"—"，不编造历史耗时）。失败只记错误类型与状态，不记供应商错误正文（审计本来就不存正文）。
- 时间口径与审计一致：库里是 UTC 朴素时间，比较用 UTC；筛选标签与"当前口径"按**北京时间**，界面显式带 `+08:00` 发送，与审计查询 / 导出共用同一个 `as_utc_naive()` 和同一件钟，避免差 8 小时。
- 前端：「运行审计」页新增「运行日志」区块（事件 / 任务类型 / 结果 / 北京时间起止 + 查询 / 清空 + 分页 + "当前口径" + 口径说明），与审计查询同页——排障时"谁点了什么"和"任务跑成什么样"要能对上同一条时间轴。列表最新在前，与审计查询一致。
- 验证：新增 `tests/unit/test_run_logs.py`（15 项：事件集合与 WHERE 子句逐条断言、任务类型走任务表子查询、口径话术与北京时间换算、入队摘要行 / 失败行 / 扫描行 / 未知类型的行映射回落、不可信字段类型不进数字）；`tests/integration/test_module6_http.py` 新增真实库 HTTP 用例（支部角色 403、入队→完成→失败三条事件的字段与耗时、事件 / 结果 / 时间窗筛选、未知取值 422、起止反向 422、跨租户不可见）；`tests/integration/test_module6_governance.py` 扩展既有队列用例钉住耗时语义：真正执行后的失败必须带实测耗时，领取时发现租约已耗尽（`lease_exhausted`）、事实上没有执行的尝试不写耗时，`asyncio.wait_for` 的超时（`TimeoutError`）分支落失败审计且 `run_once()` 正常返回（调度循环存活）；`check-roles-ui.mjs` 的「运行审计」检查补断言运行日志区块与查询入口、任务类型筛选与失败口径说明；`verify-module6.mjs` 补 `/admin/run-logs` 的界面契约（一条完成 + 一条失败）并断言时间筛选按 `+08:00` 发出、界面显示"139 毫秒"与 `HTTPException`。真机核验：`/admin/run-logs` 返回 699 条（该校 613 条执行完成 + 86 条考核提醒同步），支部角色 403、未知事件 422 且话术可直接照做；实跑一条正常任务与一条必然失败，审计行分别是 `{"kind":"member_reminders","processed":0,"duration_ms":139}` 与 `{"kind":"embedding","attempt":1,"status":"failed","error_code":"HTTPException","duration_ms":16}`，界面按事件筛"执行失败"后只剩这一行（第 1 次 / 16 毫秒 / HTTPException）。
- 边界（未做，别当成已做）：运行日志是**审计的读模型**，能回溯多久由学校配置的审计保留天数决定，不另存更长历史；`assessment_reminders_scan`（手动补扫，走 `audit_operation`）只记"跑过 / 结果"，不记生成条数（该端点 `new_value` 走统一摘要口径，条数只在接口响应里），定时扫描的条数则可见（由调度器直接落审计）；失败不记供应商错误正文，需要正文时须复现或看服务端日志；运行日志不提供导出（需要留档时用审计对账包，二者口径不同）。

### 2026-10-16（解析失败兜底 T-WF01-04）

- 问题：扫描件（图片型 PDF）、照片、旧版 Word 这三类最常见的党建材料，此前只回一句「文档解析失败: 文档不包含可解析文本」或「不支持的文件格式: .doc」——用户既分不清是文件的问题还是系统坏了，也不知道下一步做什么；「替换正文」入口更把原因吞成「文档解析失败或不含可解析文本」，等于把唯一的人工补救入口一并堵住。
- 现在按**原因**给话术，每条都给可执行出路：扫描件带**页数**说明「文件读到了，但没有文字层」（与文件损坏区分：零页 PDF 单独提示损坏），并给出 ①重导出带文字层 PDF ②另存为 `.docx / .txt` ③录入正文要点、原件作附件 三条路径；图片明确「未接入图片文字识别（OCR）」并给提取文字 / 图片转文字 / 管理员代录；`.doc / .wps` 提示「另存为 .docx，内容与格式不会丢」；表格与演示文件说明不能作为制度正文入库。
- 文案统一由 `app/rag/loader.py` 产出（`empty_text_reason` / `unsupported_reason`），入库与替换正文共用同一套；`①②③` 分步按行给出，前端错误框改 `white-space: pre-line`，不再挤成一段。
- 表单**前置告知**：上传区、耗时更长的「更新文件内容」都写明"扫描件与照片没有文字层，系统读不出正文"；文件选择器同时放开图片与旧版 Word，让用户能选中自己的文件并**看到原因**，而不是被静默拦住后以为系统不支持。
- **仍未接入 OCR 引擎**，这是本条剩余缺口而非遗漏：识别方式（本地 tesseract / PaddleOCR 或云端）与图片件能否出校属学校侧决策，敏感件不得走公网识别。定下来之前，"讲清原因 + 给出替代路径"比擅自接一个会外发图片的识别服务更符合 SEC-01。

### 2026-10-15（补记：知识库内容供给与版本维护机制 T-KB-13）

- `T-KB-13`：由 ❌ 改为 ✅。学校配置（`/admin/governance` 的「知识库供给机制」）按**权威来源**登记供给责任部门、责任人与更新周期（`knowledge_supply`，周期 30–3650 天，三者必须同时给出）；条目上只落 `maintained_at`（最近一次复核确认或内容更新）与 `next_review_at`（下次复核日期，迁移 `015_knowledge_review_schedule`），责任与周期由机制统一解析，避免同一类制度出现多套并行口径。

- 机制调整**不回溯改写**已排定的日程：已排定的复核计划是条目级承诺，悄悄改期会让"到期"失去可追溯性；新周期自下次复核起生效。存量条目按迁移口径**不**回填日程（迁移前无法判定谁供给、按什么周期复核，凭空生成只会制造一批假到期项），首次复核或下次正文更新时自然排定。
- 供给机制是"默认值来源"而非知识库使用前提：租户未登记或配置损坏时按"没有机制"处理（留日志），不让条目入库因此失败；未登记类别的条目出参里责任字段为空，前端提示「学校尚未为该权威来源登记供给机制」，而不是静默丢字段。
- 半填的机制会被拒绝：只写责任人不写周期（或反之）在前端当场拦下（不发请求），后端 `SupplyRule` 也会以 422 拒绝——只写周期没人负责、只写人没有到期提醒，两者都不能算"机制已明确"。
