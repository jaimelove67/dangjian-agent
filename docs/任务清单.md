## 0 使用说明

### 0.1 字段含义

每条任务采用统一字段：

```
- [ ] T-<模块>-<序号> | 任务名 | <优先级> | <实现状态>
      来源：FR/SEC/NFR/WF 编号
      依赖：任务 ID
      验收：可验证的完成标准
```

### 0.4 状态标记（与实现状态统一口径）

> 勾选框是 0.5「实现状态」的视觉速记，二者必须一致，不得各写一套。
> **勾选 ≠ 已通过业务验收**：验收结论以 §11.3 验收表、§1.10 必交付项对照和附录 C 里程碑为准。

| 标记 | 对应实现状态 | 含义 |
| --- | --- | --- |
| `[x]` | ✅ 已实现 | 当前工作区已有对应代码，任务转为**验收 / 加固** |
| `[~]` | ⚠️ 部分实现 | 部分完成或有明确边界未闭环 |
| `[ ]` | ❌ 未实现 / 🔒 前置闸门 | 需开发，或依赖外部确认未闭环 |

### 0.5 实现状态（校准列）

| 标记 | 含义 |
| --- | --- |
| ✅ 已实现 | 当前工作区已有对应代码，任务转为**验收 / 加固** |

| 角色 | 职责 | 关联任务 | 建议人选 |

| 电子效力确认人 | 归档留痕合规性与效力确认 | T-GATE-01、T-ORG-08 | 学校组织部门 |

### 2026-10-17（名册按支部筛选与名册统计上页面 T-MEM-02；关键节点提醒的缺口说明 T-MEM-03）

- 问题：`T-MEM-02` 的验收句是"名册支持按年度 / 批次 / **支部**筛选，并可从外部导入"。导入侧一直很完整（模板 + 预检 + 逐行报错 + 来源说明 + 权限校验），但名册只有年度与批次两个筛选：**能看到多个支部的院系 / 学校管理员只能把几个支部的人混在一张表里翻**。同一个验收句下还有第二处：`GET /member-full/stats`（名册统计）早已实现且与名册同一口径，**但没有任何页面引用**——这正是仓库里反复出现过的"功能只在接口里，用户拿不到"（`DocumentTools` 曾经就是这个下场）。顺带记下 `T-MEM-03` 的缺口：验收句点名的六个节点里，培养考察 / 材料 / 会议 / 转正都有提醒，**公示与政审没有**，而且公示连"起止日期"都没地方登记。
- 名册筛选做成"同一组条件 + 只认权限范围内的组织"：`_roster_conditions` 抽出列表与导出共用条件并新增 `org_unit_id`；统计侧 `roster_stats` 同样加 `org_unit_id` 并复用 `_scope` 与同一在册过滤。**范围外 / 已删除 / 不存在 / 没有组织的 id 一律 403**（列表、导出、统计三处一致），而不是忽略参数后回退成全量——"假筛选比没有筛选更糟"：用户会以为已经筛过，拿着整个院系的数字去开会。导出说明里写明"仅限「某支部」"，文件名标"筛选范围"；列表、导出、统计**三条链路同一口径**，不会出现"支部名册 1 人、支部统计 3 人"。

### 2026-10-17（选优结论的双人审核与团组织推优 T-MEM-13、T-MEM-06）

- 问题：这两条验收句最容易做成三件反人类的事。**一是"系统替组织下结论"**：多轮投票与培养评分都在库里，"按票数排个前几名"只要一行排序——但细则要求的是"经支委会或党员大会研究确定"，系统排出来的名单会被当成组织的结论用；**二是"一个人点两下就算认定"**：登记人自己点"通过"，复核环节实际上不存在；**三是"用年龄规则编数据"**：细则要求 28 周岁以下青年入党有团组织推优环节，可名册里根本没有出生年月——加一个"出生年月"字段并做 28 周岁校验，等于要求组织为了过校验去编一个生日，缺推优记录还会把正常选优卡死。
- 结论必须是**人填的**，系统只把依据摊开：新表 `member_selections`（`021_member_selection`）+ `/member-full/selections`，`candidates`（逐人勾选）与 `basis`（依据原文）都是必填输入；`evidence` 只是**依据快照**——本轮 `vote_summary` 的无记名汇总按拟推荐名单裁剪后存下来（票数 + `voter_count`，不含投票人身份），字段名用 `evidence_note` 以免被 `T-MEM-12` 的第三人字段脱敏规则当成正文摘掉。接口不做排序、不自动补人、不自动定等次；界面上也没有"自动生成名单"的入口（`check-roles-ui.mjs` 逐个角色断言）。
- 审核**不可绕过**：`member.scoring` 负责登记 / 修订 / 送审，审核另走 `member.stage_transition` 权限点（两个权限点分开，将来把登记与审核拆给不同角色不用改代码）；复用 `apply_review` 的"送审人不得审核自己的版本"（403）与"只接受待审核版本"（409，`reset_review` 收回审核）。**修订即回到草稿**并必须重新送审，版本只追加不覆盖（`content_revisions`，动作 `create` / `revise` / `submit` / `review` 与真实操作人）；`expected_revision` 过期一律 409，不静默覆盖别人改过的内容。
- 只向前、只同范围：目标阶段须晚于当前阶段（`StageRules.development_rank`，否则 422）、研究日期不得晚于今天（422）、一份结论只针对同一组织范围的名单（跨范围 404 / 多组织 422）——"一次支部研究"对应一份结论。**生效不等于流转**：`member_profiles.current_stage` 不动（阶段仍由授权人员按程序人工办理），并按目标阶段给 `next_step_hint` 提示该报哪一项上级备案 / 审批（细则第八条 / 第十三条 / 第二十一·二十二条 / 转正审批，条号与 `T-MEM-11` 台账同一口径，**只提示不自动报送**）。
- 团组织推优只登记事实：新表 `member_league_recommendations`（同一迁移）+ `/member-full/league-recommendations`，逐人登记推荐团组织 / 推荐日期 / 推优说明（说明按 `T-MEM-12` 分级收敛），可作废（作废后视同未发生、记录保留可查、重复作废 409）；`GET` 带 `profile_ids` 时按人回"有没有推优记录"（`has_record` / `active_count` / 最近一次日期与团组织），名册与选优结论两处共用同一判读口径。**系统不判断年龄**：不新增出生年月字段、不做年龄校验，`age_notice` 明写"系统不判断年龄……请组织核对"；**缺推优记录不阻断**选优登记 / 送审 / 阶段流转，只在结论明细里列为 `advisories` 提示——三条一起挡住"编造生日"与"卡口逼出假数据"。一次最多按 200 名党员查推优状态（超出 422）。

### 2026-10-16（组织生活会 / 民主评议党员 T-ORG-11）

- 问题：验收句"可按年度发起组织生活会与民主评议党员，记录流程、意见与整改，须人工审核与留痕"最容易做成两块互不相干的表单——组织生活会套用三会一课的表单（于是"查摆问题""批评意见"被硬塞进"学习要点""讨论共识""工作要求"下面），民主评议做成"自己填一个优秀就完事"、既不送审也不留痕。真正的反人类点有三处：**一是纪要栏目要按活动类型给**，组织生活会该记的是"查摆问题 / 批评意见 / 整改方向"，套三会一课栏目会让人把问题填进"学习要点"、把批评意见填进"讨论共识"，事后无法按栏目取用；**二是评议是"一人一年一条"的事实**，没有名单与进度就只能靠人记谁还没评、差哪些项、这条能不能送审；**三是等次是组织结论**，系统不能按票数自动排名定等次、也不能自动生成不合格处置意见——把组织结论交给系统算，等于把责任从组织身上挪开。

### 2026-10-16（三会一课频次合规提醒 T-ORG-10）

- 问题：验收句只写了"按法定频次生成提醒"，但配置里的 `activity_requirements` 本身是错的——支委会 1 次/年、党课 1 次/年、支部大会 2 次/年。照这个口径生成提醒，1 月开一次支委会就算"达标"，剩下 11 个月不会再提醒；**频次要求恰恰是靠"每个周期都要有一次"起作用的**，按年给结论等于把制度作废。而且提醒只给年度数字，不给"这个季度还差几次、最晚到哪天、现在该干什么"。真正的反人类点是**提醒不给下一步**：支部书记看到"支部大会未达标"分不清该去安排会还是该去催审核；把"已召开但纪要没过审"和"根本没开"混成一句话，前者要去做审核，后者要去开会，是两件完全不同的事。
- 口径单源：`config/business_rules.yaml` 的 `activity_requirements` 改为 `period`（`month` / `quarter` / `none`）+ `per_period`，年度次数由周期**推导**，不再单独写死一个数字（两处数字必然漂移，这次就是漂移的结果）。依《中国共产党支部工作条例（试行）》：支部党员大会每季度 1 次、党支部委员会会议每月 1 次、党小组会每月 1 次、党课每季度 1 次；`other` 设 `period: none`，不产生提醒。
- 三种状态、一句话就能照做：`met`（本周期达标）／`awaiting_review`（已召开、纪要未过审 → 提示去完成纪要审核，并写明"退回的需修订后重新提交"）／`open`（期内还差 → 给最晚日期、已安排次数、剩余天数）。完成认定**不变**：只认"已召开（`held_on` 落在周期窗口内）且 `review_status=approved`"，系统不自动认定完成。
- 跨周期不抵扣：已结束周期的缺口单独成区（`gaps`），**不会因为下个季度多开一次就消失**（本期一次性补齐当季要求即可，历史缺口仍在）。缺口按支部 × 类型聚合成一条（`missed_periods` 列表 + `missing_total` + `awaiting_total` + 自述文案），不是每个缺口一行——一个支部一年能有几十个缺口，逐行列出来等于让使用者自己汇总。
- 只按支部计算：三会一课是支部制度，给院系 / 学校节点算频次是纯噪音。选中非支部组织返回 422 并说明"三会一课频次按支部计算，请选择支部组织"；越权组织 403。前端在选了非支部节点时按**该范围内全部支部**给结论，不让使用者撞 422 才明白选错了。

### 2026-10-16（工作流运行日志查看 T-SYS-06E）

- 为什么**不新建**运行日志表 / 迁移：任务队列的每次入队（`job_enqueue`）、每次尝试失败（`job_attempt_failed`）、每次完成（`job_completed`），加上三处定时扫描（`member_scheduled_scan` / `assessment_scheduled_scan` / `assessment_reminders_scan`）本来就已经写进审计。再建一张表就是把同一事实写两遍，还会多出"两张表不一致时信谁"的问题。交付的是**读模型**：`app/services/run_log_service.py`（纯查询构造 + `RunLogRow` 行映射，可单测）＋ `GET /admin/run-logs`（权限 `admin.ops`，即「运行审计」标签那一枚；租户内可见、跨租户不可见）。
- 事件清单只有一处：`RUN_EVENTS`（动作名 → 中文阶段名）既驱动查询收窄，也经 `event_text` 给界面直接用，前端不再翻译一遍。支持按事件 / 任务类型 / 结果 / 时间范围筛选分页；未知事件或任务类型返回 422 并说明，不静默给空结果（空结果会被误读成"没跑过"）。
- 入队事件也要能看出任务类型：`job_enqueue` 走 `audit_operation`，`new_value` 按仓库统一摘要口径只留 sha256 与字节数，拿不到明文类型。解法不是在共享脱敏逻辑上开口子，而是按 `resource_id` 批量补一次任务表（一次查询覆盖当前页，不做 N+1）；任务记录已清理时留空，不编造。任务类型筛选同样按**任务表**口径（`DurableJob.kind`）：定时扫描是调度器行为、不属于某一条任务，按类型筛时不出现（用事件筛"党员提醒扫描"可单独看）。
- 耗时（`duration_ms`）是本次新增的关键字段：`run_once()` 在 `asyncio.wait_for` 外层实测尝试耗时、`execute()` 实测执行耗时，成功与失败都写入审计——排障要能区分"秒挂"（权限 403、文档失效 404）和"跑到超时"（默认 120 秒上限）。领取时发现租约已耗尽、**没有真正执行**的尝试不写数字，界面显示"—"（改动前写入的旧记录同样显示"—"，不编造历史耗时）。失败只记错误类型与状态，不记供应商错误正文（审计本来就不存正文）。
- 时间口径与审计一致：库里是 UTC 朴素时间，比较用 UTC；筛选标签与"当前口径"按**北京时间**，界面显式带 `+08:00` 发送，与审计查询 / 导出共用同一个 `as_utc_naive()` 和同一件钟，避免差 8 小时。
- 前端：「运行审计」页新增「运行日志」区块（事件 / 任务类型 / 结果 / 北京时间起止 + 查询 / 清空 + 分页 + "当前口径" + 口径说明），与审计查询同页——排障时"谁点了什么"和"任务跑成什么样"要能对上同一条时间轴。列表最新在前，与审计查询一致。
- 验证：新增 `tests/unit/test_run_logs.py`（15 项：事件集合与 WHERE 子句逐条断言、任务类型走任务表子查询、口径话术与北京时间换算、入队摘要行 / 失败行 / 扫描行 / 未知类型的行映射回落、不可信字段类型不进数字）；`tests/integration/test_module6_http.py` 新增真实库 HTTP 用例（支部角色 403、入队→完成→失败三条事件的字段与耗时、事件 / 结果 / 时间窗筛选、未知取值 422、起止反向 422、跨租户不可见）；`tests/integration/test_module6_governance.py` 扩展既有队列用例钉住耗时语义：真正执行后的失败必须带实测耗时，领取时发现租约已耗尽（`lease_exhausted`）、事实上没有执行的尝试不写耗时，`asyncio.wait_for` 的超时（`TimeoutError`）分支落失败审计且 `run_once()` 正常返回（调度循环存活）；`check-roles-ui.mjs` 的「运行审计」检查补断言运行日志区块与查询入口、任务类型筛选与失败口径说明；`verify-module6.mjs` 补 `/admin/run-logs` 的界面契约（一条完成 + 一条失败）并断言时间筛选按 `+08:00` 发出、界面显示"139 毫秒"与 `HTTPException`。真机核验：`/admin/run-logs` 返回 699 条（该校 613 条执行完成 + 86 条考核提醒同步），支部角色 403、未知事件 422 且话术可直接照做；实跑一条正常任务与一条必然失败，审计行分别是 `{"kind":"member_reminders","processed":0,"duration_ms":139}` 与 `{"kind":"embedding","attempt":1,"status":"failed","error_code":"HTTPException","duration_ms":16}`，界面按事件筛"执行失败"后只剩这一行（第 1 次 / 16 毫秒 / HTTPException）。

### 2026-10-16（解析失败兜底 T-WF01-04）

- 问题：扫描件（图片型 PDF）、照片、旧版 Word 这三类最常见的党建材料，此前只回一句「文档解析失败: 文档不包含可解析文本」或「不支持的文件格式: .doc」——用户既分不清是文件的问题还是系统坏了，也不知道下一步做什么；「替换正文」入口更把原因吞成「文档解析失败或不含可解析文本」，等于把唯一的人工补救入口一并堵住。
- 现在按**原因**给话术，每条都给可执行出路：扫描件带**页数**说明「文件读到了，但没有文字层」（与文件损坏区分：零页 PDF 单独提示损坏），并给出 ①重导出带文字层 PDF ②另存为 `.docx / .txt` ③录入正文要点、原件作附件 三条路径；图片明确「未接入图片文字识别（OCR）」并给提取文字 / 图片转文字 / 管理员代录；`.doc / .wps` 提示「另存为 .docx，内容与格式不会丢」；表格与演示文件说明不能作为制度正文入库。
- 文案统一由 `app/rag/loader.py` 产出（`empty_text_reason` / `unsupported_reason`），入库与替换正文共用同一套；`①②③` 分步按行给出，前端错误框改 `white-space: pre-line`，不再挤成一段。
- 表单**前置告知**：上传区、耗时更长的「更新文件内容」都写明"扫描件与照片没有文字层，系统读不出正文"；文件选择器同时放开图片与旧版 Word，让用户能选中自己的文件并**看到原因**，而不是被静默拦住后以为系统不支持。
- **仍未接入 OCR 引擎**，这是本条剩余缺口而非遗漏：识别方式（本地 tesseract / PaddleOCR 或云端）与图片件能否出校属学校侧决策，敏感件不得走公网识别。定下来之前，"讲清原因 + 给出替代路径"比擅自接一个会外发图片的识别服务更符合 SEC-01。

### 2026-10-15（补记：知识库内容供给与版本维护机制 T-KB-13）

- `T-KB-13`：由 ❌ 改为 ✅。学校配置（`/admin/governance` 的「知识库供给机制」）按**权威来源**登记供给责任部门、责任人与更新周期（`knowledge_supply`，周期 30–3650 天，三者必须同时给出）；条目上只落 `maintained_at`（最近一次复核确认或内容更新）与 `next_review_at`（下次复核日期，迁移 `015_knowledge_review_schedule`），责任与周期由机制统一解析，避免同一类制度出现多套并行口径。
- 日程口径：入库按「生效日期 + 周期」排定；**正文更新即一次复核**（法规修订后知识库同步更新），日程以更新时间为基准重排；维护人员登记复核（`POST /knowledge-docs/{doc_id}/maintenance`，`knowledge.manage`）后按「确认时间 + 当前周期」重排，审计动作 `maintain`。
- 到期是**维护信号**，不参与检索依据判定：`review_due` 只在条目仍现行有效（`status=effective` 且效力状态现行有效）且 `next_review_at ≤ 今天` 时为真；已废止 / 已失效 / 尚未生效的条目没有复核义务，也不接受复核登记（409）。时效与权威性仍由 `is_in_force` / `is_authoritative` 判定（T-KB-10 / T-KB-12）。
- 机制调整**不回溯改写**已排定的日程：已排定的复核计划是条目级承诺，悄悄改期会让"到期"失去可追溯性；新周期自下次复核起生效。存量条目按迁移口径**不**回填日程（迁移前无法判定谁供给、按什么周期复核，凭空生成只会制造一批假到期项），首次复核或下次正文更新时自然排定。
- 供给机制是"默认值来源"而非知识库使用前提：租户未登记或配置损坏时按"没有机制"处理（留日志），不让条目入库因此失败；未登记类别的条目出参里责任字段为空，前端提示「学校尚未为该权威来源登记供给机制」，而不是静默丢字段。
- 半填的机制会被拒绝：只写责任人不写周期（或反之）在前端当场拦下（不发请求），后端 `SupplyRule` 也会以 422 拒绝——只写周期没人负责、只写人没有到期提醒，两者都不能算"机制已明确"。
