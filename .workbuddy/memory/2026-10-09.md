## Docker 部署故障归因（镜像源）

- 现象：开发者在 GitHub 拉取本项目后在 Docker 部署，构建报 `unexpected media type text/html`。
- 结论：**不是 Docker Hub 官方限流**（限流会返回 429 + `toomanyrequests` JSON），而是 `registry-mirrors` 里的加速器返回了 HTML 错误页——请求根本没打到真 registry，manifest 请求拿到 `Content-Type: text/html`。
- 逐个源的定性：
  - `mirror.ccs.tencentyun.com`：腾讯云**内网专用**加速器，仅腾讯云 CVM 内网可用，非腾讯云机器/CI 必然失败（官方文档明确"只支持内网访问"）。
  - `docker.1panelproxy.com`：第三方公共代理，服务异常/停服时前端直接返回 HTML 错误页——正是本次报错来源。免费公共源普遍寿命短。
  - `docker.m.daocloud.io`：实测可用，可正确代理 Docker Hub。
- 关键机制：Docker 的 mirror 回退不如想象中健壮——命中一个"HTTP 层成功但内容格式不对"的 HTML 响应时，客户端直接报错，**不会自动切到列表里下一个可用源**；因此一个坏源就能让整个 pull/build 挂掉。这也是"配了三个源却等于只有一个"的原因。
- 本项目镜像清单与仓库归属（写"项目约定"便于后续排查）：
  - Docker Hub：`python:3.11-slim`、`pgvector/pgvector:pg16`、`redis:7-alpine`、`dpage/pgadmin4:latest`、`rediscommander/redis-commander:latest`
  - **非 Docker Hub**：`ghcr.io/huggingface/text-embeddings-inference:cpu-1.2` —— `registry-mirrors` 对它**完全不生效**，需单独处理（预拉+重打标签，或换源）。
- 待办建议（未实施）：清理 `daemon.json` 里的失效/专属源，只留 1~2 个实测可用的公共源；在仓库提供 `daemon.json` 模板并在 README 说明；给 Dockerfile 基础镜像加 `ARG` 前缀便于换源；`ghcr.io` 镜像考虑改用 Docker Hub 等价镜像或私有 registry。

## ⚠️ 本机 npm 装包网络路径（2026-10-09 实测，重要）

| 路径 | 到 npmmirror 延迟 |
| --- | --- |
| 平台注入代理（本会话 `127.0.0.1:30240`，**端口每次会话都变**） | 8.7s（最慢） |
| Clash `127.0.0.1:7897` | 3.9s |
| **裸连不走代理** | **3.8s（最快）** |

- **npm/pnpm 默认会读 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量**，从而走平台代理被拖慢。装包命令必须先 `export HTTP_PROXY= HTTPS_PROXY= http_proxy= https_proxy=` 清空。
- **npmmirror 的 tarball 返回 302 跳到 `cdn.npmmirror.com`**；CDN 直连正常（实测 200 / 0.97s / 150KB）。
- 首次 `pnpm install` **失败**（4m44s，exit 1），报大量 `UND_ERR_DESTROYED`：元数据请求全部成功、只有 tarball 下载连接被销毁 → **根因是高并发**（非源不可用、非网络不通）。
- **对策**：`pnpm install --network-concurrency=4 --fetch-retries=5 --fetch-retry-mintimeout=5000 --fetch-retry-maxtimeout=60000 --fetch-timeout=180000`。pnpm store 在 `D:\jaime\.pnpm-store\v11`，失败重试会复用已下载内容。
- 排查手法：用 `curl --noproxy '*' -sL -o /dev/null -w "code=%{http_code} size=%{size_download}" <tarball>` 验证源本身是否可用，再判断瓶颈在并发还是链路。

## 🚨 环境硬限制：本会话内 node 无法创建任何子进程（EBUSY）

**结论：在 WorkBuddy 会话里执行命令时，node 无法 spawn 任何子进程；因此一切会 fork 的 node 工具链（pnpm 的 postinstall/build 脚本、vite、esbuild、turbo）在会话内都无法运行。**

实测证据（`probe` 脚本，已清理）：

- `spawnSync(process.execPath, ['--version'])` → `EBUSY`，`errno: -4082`（libuv `UV_EBUSY`，即 Windows `CreateProcessW` 返回 `ERROR_BUSY(170)`）
- 目标换成 `cmd.exe` / `where.exe` / `bash.exe` → **全部 `EBUSY`**
- `execSync` / `execFileSync` / `spawnSync` / `spawnSync+shell:true` → **全部 `EBUSY`**
- 托管 node（22.22.2）与系统 node（24.14.0）**同样失败**
- 但 **bash → node 是可以的**（bash 能正常启动 node 执行脚本）

**关键推论**：这是执行进程树的限制（受限 job object），**不是** WorkBuddy 的 `dangerouslyDisableSandbox` 能绕过的——已实测加该参数后报错完全一致。**也不是**源/网络/并发问题（低并发 `--child-concurrency=1` 同样失败）。

**影响**：`pnpm install` 必然停在 postinstall（`esbuild` 的 `install.js` 要 `execFileSync(node, [bin,'--version'])` 校验二进制）；即使装完也无法在会话内 `pnpm dev`（vite 要 spawn esbuild 子进程）。

**处理约定**：
- **不要在会话内尝试跑前端 dev/build**，会浪费大量时间。前端必须由**用户在自己终端**运行。
- 会话内的合理工作范围：用文件工具写代码、`git` 操作、`curl` 探测、python 脚本（python 不 fork 时可跑）。
- 若必须验证前端，考虑改用「直接产出可视化设计稿」而非跑工程。

### ⚠️ 踩到的坑：vben 没有引入部分 Element Plus 组件样式

`apps/web-ele/src/adapter/component/index.ts` 只按需引入了 button / checkbox / date-picker / divider / input / input-number / radio / space / switch / time-picker / tree-select / upload / select-v2 的 `style/css`，**没有 table、table-column、pagination、tag、select、option、message**（vben 的表格用的是 vxe-table，不是 el-table）。
后果：直接用 `el-table` / `el-pagination` / `el-tag` 会渲染成裸样式。
**对策**：在需要这些组件的 SFC 顶部显式补 `import 'element-plus/es/components/<name>/style/css';`（已验证这些路径在 element-plus 2.14.5 下全部存在）。**不要**用 `element-plus/dist/index.css` 全量引入，否则可能把 vben 的主题变量覆盖回默认蓝。
